# GoTask 开发计划

> 本文档汇总项目底层逻辑、Go 语言边界、精简/优化判断、同类项目对比，以及「当前分支优化 + 重构分支执行模型」的双主线开发计划与当前执行状态。

## 1. 项目定位与终极意图

GoTask 的真实目标不是“定时任务框架”，而是**进程内的任务生命周期内核**：用任务树统一管理组件的启动、运行、停止、重试、资源回收和观测。

核心抽象不是“执行一个函数”，而是：

> 任务由谁创建、归谁管理、何时算启动成功、如何停止、停止后谁负责清理，以及失败后是否重新运行。

每个任务同时具有四种身份：

1. **生命周期对象**：初始化、启动、运行、销毁等状态。
2. **树节点**：拥有父任务、子任务和层级关系。
3. **`context.Context`**：停止信号和停止原因沿任务树传播。
4. **可观测对象**：ID、状态、启动时间、停止原因、重试次数等。

## 2. Go 语言的硬边界

| 目标 | 可行性 | 判断 |
|---|---|---|
| 服务内任务树、生命周期、协作停止、重试、观测 | 高 | Go 很合适 |
| 强超时、强隔离、资源配额、可靠热重启、跨进程恢复 | 中高 | Go 可实现，但需引入进程/外部机制 |
| 单进程内像 OS 一样强杀任意任务、隔离 OOM、精确控制资源 | 不可行 | 运行时与地址空间模型的硬边界 |

关键限制：

- **无法强制杀死 goroutine**：`Stop()` 只取消 Context，无法终止忽略 Context 的任务、无超时 I/O、不返回的 `Dispose`、死锁或长期持锁代码。需要强杀应把任务放进独立进程由 supervisor 终止。
- **无法提供任务级内存/故障隔离**：所有 goroutine 共享地址空间、堆、调度器、进程故障域；OOM、运行时 fatal、cgo 崩溃不是 `recover` 能可靠解决的。
- **无法提供硬实时/精确资源配额**：Go 不支持给 goroutine 设置 CPU 优先级、配额、硬截止时间；抢占不等于取消。
- **无法透明热替换运行代码和状态**：需显式设计 socket 交接、状态序列化、drain 与退出。

**结论**：不会因为 Go 而无法完成项目的合理终极意图；但若意图被定义为“在单 Go 进程内模拟具有强杀、强隔离、精确资源控制和透明热替换能力的操作系统”，则不可行，且非 Go 独有。

## 3. 精简与优化判断

### 3.1 应精简

- **泛型编排可独立或缩减**（`generic.go` 与任务树几乎无共享状态，却重复维护执行入口、重试、超时、并行）。
- **类型化配置替代 `opt ...any`**（`job.go` 的 `initContext` 用 `runtime.Caller` 推断调用栈深度，错误只能运行时暴露）。
- **弃用指针身份 API**（`GetTaskPointer` / `FromPointer` 用 `uintptr`，不能跨进程/跨重启，且绕过 GC 安全边界）。
- **收缩小型过度抽象**（如 `Singleton[T]` 目前主要服务事件循环 channel 懒初始化，可内聚为私有实现）。
- **Dashboard 与 README 瘦身**：Dashboard 移入独立示例/可选模块；SQLite/GORM 历史默认关闭；README 只保留核心模型与可编译示例；详细 API 交给 GoDoc。

### 3.2 不应为精简而删的核心

- 任务树与父子级联销毁；
- 启动完成与销毁完成的分别等待（`startup` / `shutdown` Promise）；
- `Using` / `OnStop` / `OnDispose` 的不同清理阶段；
- 晚注册钩子、重试代际（`hookGen`）和事件循环重启保护；
- `TickTask` 与 `AsyncTickTask` 的不同执行语义；
- 业务 Key 与内部任务 ID 的区别。

`Run` 与 `Go` 不能只为了减少接口而直接合并：当前一个同步占用事件循环，另一个启动独立 goroutine。长期更合理方向是让事件循环只负责生命周期控制，避免长 `Run` 阻塞父循环；若未来统一执行模型，再在重大版本中合并接口。

### 3.3 优化优先级

- **P0 正确性**
  1. `RunTask` 失败路径拒绝了错误的 Promise（`task.go` `RunTask`）。
  2. `Job.Call` 忽略入队失败，可能让调用方无谓等待（`job.go` `Call`）。
  3. `start()` 重试循环未每轮清空 `err`，导致无 `Start` 的 `Run` 任务跳过新一轮执行却仍消耗重试次数（`task.go` `start`）。
  4. `checkRetry` 重试退避用同步 `time.Sleep`，不可取消且阻塞事件循环（`task.go` `checkRetry`）。
  5. 事件循环对 recovered 值直接 `err.(error)`，`panic("text")` 会二次 panic（`event_loop.go`）。
  6. `RangeSubTask` 忽略了 callback 返回值（`job.go`）。
- **P1 把事件循环变为可靠控制平面**：长时间 `Run` 阻塞父循环、阻塞式 `Start`/`Dispose`/钩子、重试中不可取消 sleep、子任务销毁无统一超时/升级策略。
- **P2 性能**：`reflect.Select` 不一定需立刻替换；先基准再考虑分片事件循环、固定通知通道、减少动态 SelectCase 重建、一致性快照、背压。

## 4. 同类 / 更优项目对比

| 项目 | 关系 | 更合适场景 |
|---|---|---|
| [thejerf/suture](https://github.com/thejerf/suture) | **最接近**，Erlang 风格监督树 | 主要需要服务监督、失败重启、监督树，模型更专注 |
| [oklog/run](https://github.com/oklog/run) | 极简组件生命周期组 | 只需管理 `main` 中若干组件，任一退出后整组关闭 |
| [sourcegraph/conc](https://github.com/sourcegraph/conc) | 结构化并发、任务池、panic 传播 | 主要需要并行函数、结果收集、并发限制，可替代部分泛型编排 |
| [golang.org/x/sync/errgroup](https://pkg.go.dev/golang.org/x/sync/errgroup) | 标准生态并发错误传播 | 需求简单，少依赖 |
| [uber-go/fx](https://github.com/uber-go/fx) | 依赖注入与应用启停生命周期 | 大型应用依赖组装、启动顺序和关闭钩子，非监督树 |
| [hibiken/asynq](https://github.com/hibiken/asynq) | Redis 持久化分布式任务队列 | 延迟任务、重试、多 worker、崩溃恢复、管理界面 |
| [riverqueue/river](https://github.com/riverqueue/river) | PostgreSQL 持久化任务队列 | 已用 PostgreSQL，任务入队与业务事务结合 |
| [go-co-op/gocron](https://github.com/go-co-op/gocron) | 专注定时调度 | 真正需求只是 cron、周期执行和调度策略 |

**结论**：不存在全面上位替代。Suture 最值得对标，但 GoTask 的差异化是动态任务树、Channel/定时直接入模型、细粒度钩子、泛型编排、状态和 Dashboard。不建议与 Asynq/River 正面竞争持久化分布式队列。

## 5. 双主线开发计划

### 5.1 当前分支（main）：稳定优化线

- 只做**不改变核心执行语义**的工作。
- 修复 P0 正确性项（见 3.3）。
- 补充测试、`go test -race`、基准测试。
- 类型化配置、文档修正、废弃 API 标记。
- 小范围提取重复实现。
- Dashboard / 泛型编排解耦准备。
- 始终保持可发布，暂不改变 `Run`/`Go`、钩子和事件循环执行约定。

### 5.2 重构分支（refactor/execution-model-v2）：执行模型演进线

- 工作树：`E:/project/gotask-execution-model-v2`（已基于 `main` 创建）。
- 集中处理：事件循环只承担生命周期控制；长业务执行与控制平面分离；重新评估 `Run`/`Go` 是否仍需区分；统一启动/运行/停止/销毁超时语义；重试与监督策略分离；任务状态/快照一致性；泛型编排与任务树边界；可选 Dashboard/历史/持久化。

**四阶段（小步重构，避免长期失控大分支）**：

1. **语义基线**：补全当前行为测试与基准，明确兼容与可改边界。
2. **控制与执行分离**：先让 `Run` 不再阻塞父事件循环，保留旧 API 适配层，观察状态机/重试/销毁受影响面。
3. **统一生命周期与监督策略**：处理 `Run`/`Go`、停止超时、销毁超时、重试状态、故障升级。
4. **外围渐进增强**：泛型编排、Dashboard、历史记录、扩展接口，避免与核心重构互相干扰。

### 5.3 同步规则

- 当前分支的正确性修复及时同步到重构分支。
- 不把重构分支的执行语义反向同步到当前分支。
- 当前分支尽量不再增加大型新功能。
- 定期将当前分支合并进重构分支，尽早暴露冲突。
- 公共测试尽量复用，执行语义不同的地方用独立契约测试表达。

### 5.4 验收门槛（每阶段）

- 核心测试通过；`go test -race` 通过。
- 任务阻塞、停止、重试、销毁、晚注册钩子有专项测试。
- 基准证明无明显退化。
- 旧 API 有适配层或明确迁移路径。
- Dashboard 与示例仍能运行。
- 文档描述与真实语义一致。

## 6. 当前执行状态

### 6.1 main 分支已完成

**P0 正确性六项（3.3 列表）全部完成**：

- `task.go` `RunTask`：失败时只拒绝待运行子任务并取消其 Context，不再污染接收者启动 Promise。
- `job.go` `Call`：入队失败时显式取消等待；回调 `defer cancel()` 保证 panic 时也能返回。
- `task.go` `checkRetry`：重试退避改为可被父任务 `Done()` 打断的 `time.Timer` 等待，等待后重新检查父任务状态。
- `task.go` `start`：重试循环每轮清空 `err`，修复无 `Start` 的 `Run` 任务跳过执行却消耗重试次数的缺陷（同时移除每轮 `ResetRetryCount`，否则 `MaxRetry` 永远无法生效——有限重试测试锁定）。
- `job.go` `RangeSubTask`：返回 `callback` 的提前终止信号。
- `event_loop.go`：recovered 任意值安全转换为 `error`（`fmt.Errorf("%v", err)`），避免字符串 panic 二次 panic。

**并发正确性与销毁顺序（挂死/竞争类，测试门放行后集中清理）**：

- `task.go` `Stop`/`dispose`/`reset`：`stopOnce sync.Once` 换成 `stopMu + stopped + stopErr`。`Once.Do` 的快速路径（`done.Load()==1`）完全不碰互斥量，goroutine 在 `done.Store(1)` 与 `m.Unlock()` 之间的窗口，与 `reset()` 对 Once 结构体的整体覆写构成无序竞争（race detector 实测：reset 的 8 字节结构体写 vs goroutine 的 sema 写）。互斥量版让 `dispose()/reset()` 必须拿锁，永远排在在途 `Stop` 临界区之后。
- 提前 `Stop` 挂死修复（`Test_Hooks` 10 分钟超时的根因）：`Stop` 先于 `AddTask` 时，停止请求被记住（`stopped/stopErr`），`initContext` 建好 context 立即补取消；出生即停止任务的 startup promise 改挂 `context.Background()`，否则 `Fulfill` 被已取消父 context 吞掉，`WaitStopped` 跳过 shutdown 等待、钩子没跑调用方就拿到返回值。`start()` 错误路径显式 `startup.Reject(err)` 落定 promise。
- Debug 饥饿求值竞争：`Stop()` 的日志参数会跨 goroutine 读 `ID/handler/parent/startup/StartTime` 等字段（`Test_Block` 定时器 goroutine 与 `AddTask` 实测）。修复：`initContext` 整体纳入 `stopMu`（`handler` 赋值从 `AddTask/RunTask` 内嵌进来）、`reset()` 的 Context/promise 重建纳入 `stopMu`、`Stop()` nil 检查移入锁内、新增 `startNano atomic.Int64` 快照供跨 goroutine 读 elapsed（公开字段 `StartTime` 类型不变）。
- `event_loop.go` `initCases`：`run()` 重启时按 `e.children` 重建子任务信号 case。panic 后重启原本只剩输入通道一个 case，子任务永不被 dispose、`waitChildStopped` 永久挂起、父循环被拖死引发级联超时（`TestEventLoopRecoversStringPanic` 触发过该路径）。
- 父子销毁顺序：`waitChildStopped` 改等子任务的 `shutdown`（dispose 整个跑完才落定），不再用会被 Reject 短路的 `WaitStopped()`——后者使父任务的 OnDispose 与子任务 dispose 并发甚至抢先执行，打破"子任务先于父任务销毁"约定（`Test_ParentStop` 实测父钩子跑到子钩子前面）。配套补齐两处 shutdown 无落定机会的路径：`AddTask` 入队失败（任务永不进事件循环）、事件循环 65535 子任务门禁（停止后补走一遍 dispose，同时修复任务滞留 children 撑住 Size 的泄漏）。

**测试与基准**：

- 重写 `Test_Hooks`：原写法（先 `Stop` 再 `AddTask`）编码了从未存在的语义；"已停止任务不跑 OnStart 钩子"是 `drainStartHooks` 护栏自始至终的 deliberate 语义，改用正常启动后停止验证钩子注册顺序。
- 新增 `Test_StopBeforeAddTask`：锁定提前停止后的真实语义（OnStart 不跑、OnDispose 跑、WaitStopped 返回停止原因）。
- 修复 `Test_ParentStop` 同步缺陷：原写法只等子任务 `WaitStopped`，父钩子跑到测试完成后触发 `Fail in goroutine after ... has completed` panic；也不能改等 `parent.WaitStopped()`（start 错误路径 startup 被 Reject 时会提前返回），改用两个 OnDispose 钩子各发一个信号定序。
- 新增 `stability_regression_test.go`（RunTask 拒绝、Call 背压、可取消退避、遍历终止、Run/Go 有限重试、事件循环字符串 panic）与 `benchmark_test.go`（四条路径基线）。
- **验收门**：全量 `go test -race -count=1 .` 通过；顺序敏感测试 `-count=30` 加压通过；修复前后基准对比（TaskStartStop ~8.4μs、JobStopWithLiveChildren ~97μs、JobCall ~1.9μs、StopIdempotent ~215ns）差异均在噪声内，无明显退化。
