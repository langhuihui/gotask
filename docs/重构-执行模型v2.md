## 1. 当前执行模型事实（代码走读结论）

| # | 事实 | 代码位置 |
|---|---|---|
| F1 | 每个 Job 一个事件循环 goroutine，懒启动（首个入队或有子任务时 `active`） | `event_loop.go` `active/run` |
| F2 | 循环单 goroutine 串行处理两类消息：输入（ITask 启动 / `func()` 回调）与子任务信号（`Done`/`Tick`） | `event_loop.go` `run` 主循环 |
| F3 | `TaskBlock.Run()` **在事件循环上同步执行**：阻塞期间同 Job 的 Call、其他子任务启动、子任务停止信号全部排队 | `task.go` `start` → `runHandler.Run()` |
| F4 | `TaskStarter.Start()` 同样在循环上同步执行 | `task.go` `start` → `v.Start()` |
| F5 | `TaskGo.Go()` 在独立 goroutine 执行（`go task.run(...)`），不占循环 | `task.go` `start` → `go task.run` |
| F6 | 子任务的 start/dispose 由所属 Job 的循环驱动；跨 Job 隔离（子 Job 循环阻塞不拖累父 Job 循环） | `event_loop.go` + `job.go` `onChildDispose` |
| F7 | 重试路径（checkRetry 退避 → reset → 再 start）整条在循环上 | `task.go` `start` 错误路径 |
| F8 | 钩子在事件循环上执行；晚注册的补跑可能落在注册方 goroutine | `task.go` `drainStartHooks/drainDisposeHooks` |
| F9 | dispose 顺序：Job 先 `waitChildrenDispose`（等齐每个子任务 shutdown）再跑自身钩子 → **子先于父**（`7a62329` 修复锁定） | `job.go` `waitChildrenDispose/waitChildStopped` |
| F10 | `Stop()` 可从任意 goroutine 调用：取消 context + 排空 closeOnStop；dispose 在循环上异步执行 | `task.go` `Stop/stop/dispose` |
| F11 | `WaitStarted`/`WaitStopped` 双 promise；`WaitStopped` 在 startup 被 Reject 时提前返回（不等 dispose） | `task.go` `WaitStopped` |
| F12 | **TaskBlock 子任务的 `Start → OnStart 钩子 → Run →（失败）dispose → 退避 → reset → 再 Start` 整条生命周期内联在事件循环的路径 A**；运行期不在 `e.children`（信号 case 从未登记），循环与 `initCases` 重启都看不到它 | `task.go` `start` 错误路径 |
| F13 | `util.Promise.Fulfill(nil)` 落 `ErrResolve` 原因、`Await` 映射回 `nil`；TaskBlock 子任务的 `startup` 在 Start 成功时即落定（`WaitStarted` 返回 `nil`），Run 之后的 `Reject` 是空操作 | `util/promise.go` |
| F14 | 旧代码缺陷（Phase 2 顺带修复）：Run panic 被 `start()` 的 defer 恢复后，错误路径（`startup.Reject/Stop/onChildDispose/checkRetry`）整个被展开跳过，`start()` 返回零值 false——任务被 `removeChild` 却永不停止、永不销毁（`WaitStopped` 永久挂起） | `task.go` `start` defer |
| F15 | **Phase 2 后**：TaskBlock 的 `Run` 在独立 goroutine 执行（复用 `task.run`，与 TaskGo 同构），`start()` 随即返回 true，子任务转入路径 B 信号驱动；执行期间父循环保持响应 | `task.go` `start` TaskBlock 分支 |

**核心病灶**：F3/F4/F7 —— 控制平面（循环）与业务执行（Run/Start/退避）共用同一个 goroutine。一个长 `Run` 就让整个 Job 的停止响应、兄弟任务、`Call` 全部停摆（`ai_rules/Claude.md` 里"单 goroutine 事件循环"约定正是为此而立，Phase 2 要解开的也正是这个结）。

> 注：F3/F7/F12 是 Phase 1 走读时（旧实现）的事实；Phase 2 已改写 F3/F12 的执行位置（见 F15），F4（Start 同步）与 F7（退避占循环）现状保留，留待 Phase 3 评估。

设计文档 `重构-执行模型v2-Phase2设计.md`（提交 `418679b`）。实施改动仅两处代码 + 两个测试文件：

| 改动 | 文件 | 内容 |
|---|---|---|

| `RunTask` 驱动协议化 | `task.go` | 调用方 goroutine 上复刻路径 B 协议（`<-Done → dispose → checkRetry → reset → start` 循环） |

### 4.2 基准对比（基线见 §2，本机 32 核）

| 基准 | Phase 1 基线 | Phase 2 | 变化 |
|---|---|---|---|
| BenchmarkTaskStartStop | ~8 500 | ~10 900 | **+31%**（理由见下） |
| BenchmarkJobStopWithLiveChildren | ~97 600 | ~101 300 | +3.8% |
| BenchmarkJobCall | ~1 900 | 噪声内 | — |
| BenchmarkStopIdempotent | ~215 | 噪声内 | — |
| BenchmarkCallDuringBlockingRun | 旧语义下不可能（Run 占循环，Call 只能排队） | 2 069 | **新能力** |

TaskStartStop +31% 的理由（实施前已批准记录）：`start()` 对 TaskBlock 多出一次 goroutine spawn 与信号汇合路径（context 取消 → 信号 case → 循环下一轮处理），换来的正是 C1「Run 不占循环」的核心目标；该基准测的是「启动即停止」的纯控制路径，是全部基准中最贴近本次改动成本的一个，绝对值仍在 11μs 量级，其余基准均在阈值内。

### 4.3 行为变化清单（对使用方，均有契约或设计文档记录）

1. `onDescendantsStart` 对 TaskBlock 子任务由「从不触发」变为「首次 spawn + 每次重试各一次」（R2/Q1，已批准接受；语义上更正确——子任务确实启动了）；
2. `RunTask` 对 TaskGo / 纯 TaskStarter 也统一走重试判定（旧实现不重试），与事件循环路径协议对齐（Q2，已批准接受；「同一子任务经 AddTask 会重试、经 RunTask 不重试」本身是既有不一致）；
3. `Blocked()` 在 Run 期间对 TaskBlock 子任务返回 `nil`（仅 dashboard 展示差异）；
4. Run 期间对同 Job 的 `AddTask`/`Call` 从「入队延迟、Call 可能死等」变为「立即处理」（F3 病理的直接修复）；
5. 运行中的 TaskBlock 子任务出现在 `e.children` 中（信号 case 已登记，`initCases` 重启可覆盖）；
6. F14 缺陷顺带修复：Run panic 不再导致任务被 removeChild 却永不停止/销毁（C11）。

**原定硬约束核销**：C2/C4/C6/C7 与 main 已锁定行为无回归（全量 -race + 30 轮加压）；`Run`/`Go` 接口签名未动，只改执行位置；状态机对外可观测序列不变（设计文档 §3.4 对照表逐项核对）；重构线执行语义未反向同步回 main。
