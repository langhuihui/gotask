## 3. 决策一：发布形态（模块路径与分支）

### 3.1 为什么必须动 import path

Go modules 的硬规则：主版本 ≥ 2 时，module path 必须带 `/vN` 后缀，否则 `go get` 会拒绝 `v2.0.0` 这个 tag（除非用 `+incompatible`，那是给未启用 modules 的上古代码留的，会让依赖失去所有 modules 保障）。

所以「发一个真正的 v2」和「保持 `github.com/langhuihui/gotask` 不变」是互斥的。二者必选其一：

| 方案 | 形态 | 老用户影响 | 代价 |
|---|---|---|---|
| **A. 真断代（推荐）** | module → `github.com/langhuihui/gotask/v2`，tag `v2.0.0` | 零影响，继续 `go get ...gotask@v1.0.5` | 下游要改一行 import + 可能的 API 改名 |
| B. 软 v2 | 路径不变，发 `v1.6.0`，破坏性变更全部降级为「新增 API + 旧 API Deprecated」 | 零影响 | 「v2」只存在于 README；`Run`/`Go` 永远合并不掉，Deprecated 永远删不掉——等于把 G1/G2 无限期搁置 |
| C. `+incompatible` | 路径不变，tag `v2.0.0+incompatible` | 需要手动 `@v2.0.0+incompatible` | 失去语义化版本校验，生态不友好 |

**推荐 A。** 理由：G1/G2 是这次重构最后的两笔账，软 v2 等于把它们变成永久技术债；而 A 的代价被主版本号本身隔离了——不想改的用户停在 v1 即可，v1 分支继续收 bug 修复。

### 3.2 分支与维护线

推荐：**`refactor/execution-model-v2` 就是 v2 的开发线**，完成后直接打 `v2.0.0`，不合回 `main`。

- `main` 保持 v1 维护线：只接受 bugfix / 安全修复，继续打 `v1.0.x`。
- 债务清零后的第二个版本再考虑把 `main` 切到 v2（或直接在 v2 线上长期演进）。
- 好处：v1 用户在 `go get ...gotask` 上永远拿到一个「虽然旧但能跑」的版本；v2 的破坏性变更不需要在 `main` 上反复解释。

### 3.3 仓库内受影响的 import

| 位置 | 处理 |
|---|---|
| `dashboard/server/go.mod`（独立 module `gotask-example`） | `replace github.com/langhuihui/gotask => ../..` 改为 `replace github.com/langhuihui/gotask/v2 => ../..`，`require` 同步改 |
| `lessons/`、`lessons_CN/` | 同 module 同包，**无需改 import**（它们用的是包内符号） |
| `README*.md` / `docs/*` | 示例 import 全量替换 |

## 4. 方案设计

### 4.1 V-A：`Run` / `Go` 合并

**目标形态**：删除 `TaskGo`，只保留一个执行接口。

```go
// TaskRun 是任务的执行体：在独立 goroutine 中运行，返回即表示本轮结束。
// 返回 nil 触发框架自动 Stop(nil)；返回 error 触发 Stop(err) 并按重试配置处理。
type TaskRun interface {
    Run() error
}
```

命名取舍见 §5 的 R1。**保留方法名 `Run`**：README 里 9 处、下游绝大多数任务都是 `Run() error`，改这个名字等于让所有人改一遍；`Go` 只有 1 处（`AsyncTickTask`）。

**`start()` 的收敛**：现在 `TaskBlock` 与 `TaskGo` 是两段几乎逐行相同的分支（`task.go:961-1000`），合并成一段：

```go
if runHandler, ok := task.handler.(TaskRun); ok {
    task.setState(TASK_STATE_RUNNING)
    attemptDone := make(chan struct{})
    task.setAttemptDone(attemptDone)
    go task.run(runHandler.Run, attemptDone)
    return true
}
```

净减约 20 行重复，且顺带消灭「同时实现 `Run` 和 `Go` 时谁优先」这条从未写进文档的隐式规则。

**`AsyncTickTask`**：`Go()` → `Run()`（`channel.go:63`）。

**行为变化与静默破坏风险（实施前发现，关键）**：

删掉 `TaskGo` 后，**方法名 `Go()` 本身不会消失**——它只是不再被框架识别。于是有一类迁移会「编译通过、行为错误」：

```go
// v1：这是一个正常执行的任务
func (t *MyTask) Go() error { /* 主循环 */ }
// v2：TaskGo 已删除 → start() 找不到执行体 → 任务 STARTED 后什么都不做，
//     一直挂到被外部 Stop。没有报错、没有日志、没有 panic。
```

这比编译错误危险得多：v1 里「同时实现 `Run` 和 `Go`」的任务本来也只跑 `Run`，所以静默忽略更隐蔽。因此 v2 必须加一道**迁移守卫**：

```go
// ErrLegacyTaskGo：handler 仍只实现 v1 的 Go() 而不实现 Run()。
var ErrLegacyTaskGo = errors.New("task: Go() is no longer a task entry point; rename it to Run() error")

if task.handler 实现了 interface{ Go() error } && 未实现 TaskRun {
    task.startup.Reject(ErrLegacyTaskGo)
    task.Stop(ErrLegacyTaskGo)   // 走已有的失败路径：可诊断、可重试
    return false
}
```

这样「只实现 `Go()` 的任务」在 v2 下**立刻以明确原因失败**，而不是空转。`ErrLegacyTaskGo` 与 `ErrNotTickTask` 一并纳入 `isFailureReason`（算失败、可重试），使 `FailurePolicy{Escalate}` 能感知。

守卫只在 handler 未实现 `TaskRun` 时才触发，正常实现 `Run()` 的任务零开销（一次接口断言）。

**任务类型状态**：`TASK_STATE_GOING`（=「Go 分支已启动」）失去意义，与 `TASK_STATE_RUNNING` 合并。保留常量值以免 `TaskState` 的数值移位，但标注 `Deprecated`——或者直接在 v2 删掉并重排（状态是 byte，Dashboard 按字符串展示，不依赖数值）。推荐**删掉**，理由同 G2：v2 不做半吊子。

### 4.2 V-B：`Deprecated` 清仓

| 符号 | 位置 | 处理 | 仓库内使用者 |
|---|---|---|---|
| `FromPointer(uintptr) *Task` | `task.go:213` | 删 | 无 |
| `(*Task).GetTaskPointer() uintptr` | `task.go:363` | 删 | 无（4B 已改 ID） |
| `Singleton[T]`（含 `Load`/`Get`） | `event_loop.go:15` | 删（内部用 `lazyChan`） | 无 |
| `AnyTaskFunc` + `(AnyTaskFunc).Run` | `generic.go:60` | 删 | 无 |
| `AdaptAnyTaskFunc` | `generic.go:249` | 删 | 无 |
| `AsAnyTaskFunc` | `generic.go:256` | 删 | 无 |
| `(*Task).GetKey() uint32` | `task.go:367` | 删（F49 同名不同义；要 ID 用 `GetTaskID`） | 无 |
| `initContext` 的 `case int` | `job.go:329` | 删（用 `WithCallDepth`） | 框架内 3 处，改传 `WithCallDepth` |

**关于 `GetKey()` 的替代**：`WorkCollection` 的 key 由 handler 自己实现的 `GetKey() K` 决定（经反射的 `getKey()`），与 `Task.GetKey() uint32` 无关。删掉后者不影响集合语义，只堵住一个误用入口。

**关于 `AsAnyTaskFunc`**：它是「typed → any」的桥。删之前确认没人用它——是的，零使用者。若将来需要，`TaskFunc[any]` 直接转换即可。

### 4.3 V-C：异步 dispose（评估结论：不做）

**想解决的问题**：`waitChildrenDispose` 同步阻塞，一个慢 `Dispose()` 会拖住整个父事件循环（F46）。3B 的 `SetDisposeTimeout` 只能事后打日志，`SetStopTimeoutDetach` 也只能让**父**放弃等待，不能解决「父循环本身被占住」。

**如果要做，必须先立的新契约**（这是 3B.2 否决时留的话）：

> **D-1**：`Task.WaitStopped()` 返回 ⇒ 该任务自身已 `DISPOSED`。（不变）
> **D-2**：`WaitStopped()` 返回 ⇒ 其**整棵子树**已 `DISPOSED`。（v1 成立；异步化后**只能降级为「停止信号已下达」**）
> **D-3**：父任务 `DISPOSED` 之后，不再有任何子任务的钩子在该父的 goroutine 上执行。

D-2 的降级是真正的问题：Monibuca 依赖「父停止返回后，所有子任务的 goroutine 已退出、资源已释放」这一强保证来做重连/换源。把它改成「已下达」会让所有既有调用方要在每个停止点后自己轮询子树，收益（省一次阻塞）远小于风险面。

**结论：v2 不做。** 已有逃生门足够：
- `Job.SetStopTimeout(d)` —— 等子任务超过 `d` 就不再等；
- `Job.SetStopTimeoutDetach(true)` —— 超时后不级联上抛父级；
- `Task.SetDisposeTimeout(d)` —— 记录慢销毁并给出 `disposeProcess` 段快照。

若将来要做，正确形态是**新增 opt-in** `Job.SetAsyncDispose(true)` + `Job.WaitDescendantsDisposed()`，让调用方显式选择放弃 D-2——而不是改默认语义。登记为 v3 候选。

### 4.4 V-D：开放 `ITask` 给外部包（评估结论：不做）

**问题本质**（F45）：`ITask` 混了两层——「用户可见的任务契约」与「事件循环内核协议」。未导出方法（`start`/`dispose`/`checkRetry`/`reset`/`keepalive`/`getKey`）把接口锁死在包内。

**如果要做**：拆成

```go
type ITask interface {           // 用户可实现的公开面
    context.Context
    GetParent() ITask
    GetTask() *Task              // 仍要求返回内部 *Task → 事实上仍不可实现
    ...
}
```

卡点在 `GetTask() *Task`：公开面要求返回具体内部类型，外部实现者得先造一个 `*Task`，而 `*Task` 的字段大多私有、构造只能经 `AddTask`。要真正开放，得把 `GetTask()` 也从公开面拿掉，改成 `Job.AddTask` 返回 `*Task` 并让调用方自己存句柄——这会波及全部 `handler.(ITask)` 断言与 `task.GetTask()` 调用点。

**结论：v2 不做。** 理由：
1. 现状的「嵌入 `Task`」已经覆盖了 99% 的自定义需求（`WorkCollection`、`ChannelTask`、`TickTask` 都是这么做的）；
2. 零下游证据表明需要「不嵌入也能实现」；
3. 这是纯结构性重构，风险高、语义收益为零，不该和 API 收口混在一个版本里。

替代方案（若确有需求）：v2 先提供一个**组合式**入口 `task.Wrap(handler any) *Task`，把「包装」做成函数而不是接口实现。登记为 v3 候选。

### 4.5 V-E：零散收口

| 项 | 现状 | v2 |
|---|---|---|
| `TickTask.Start` 裸断言（F48） | `t.handler.(ITickTask).GetTickInterval()` | 先 `if _, ok := t.handler.(ITickTask); !ok { return ErrNotTickTask }`，把 panic 变成启动失败（走 `start()` 已有的 `err` 路径 → `Stop(err)` → 可重试可诊断） |
| `AsyncTickTask.Run`（原 `Go`）同 | `t.handler.(ITickTask).Tick(nil)` | 同上 |
| `case int` callDepth（F47） | 裸 `int` | 删；框架内 3 处改 `WithCallDepth(n)` |
| `TASK_STATE_GOING` | 与 `RUNNING` 并存 | 删（V-A 合并后无意义） |

新增错误值 `ErrNotTickTask`，与既有 `ErrTimeout` / `ErrChildFailed` 并列，并纳入 `isFailureReason` 的失败判定（要求：算失败、可重试）。

## 5. 选型记录

| # | 议题 | 选择 | 备选与否决理由 |
|---|---|---|---|
| R1 | 合并后的接口名 | `TaskRun`（`interface{ Run() error }`） | `Runnable`——Go 惯例但破坏 `Task*` 前缀一致性；`TaskExecutor`——过长；保留 `TaskBlock`——Phase 2 后「Block」已名不副实，名字本身在骗人 |
| R2 | 保留的方法名 | `Run` | `Go`——只有 1 个实现者但 README 9:1 落后；`Execute`——无历史包袱但迁移面最大 |
